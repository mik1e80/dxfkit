## 项目简介

dxfkit 是一个用 MoonBit 实现的 DXF（CAD 图纸）工具链，回答一个问题：
**这份图纸能不能上机床**（激光切割 / CNC 加工）。它把图纸解析成世界坐标
的折线几何，然后做加工前检查：轮廓闭合、自相交、重复切割、最小间隙、
退化几何、文字未转曲线。库本体零第三方依赖，同一份代码编译出库、
命令行、网页三种用法；47 个真实文件回归，206 项测试全过。

## 核心功能范围

- **加工前检查**：轮廓闭合（报缺口宽度和位置）、自相交、重复切割、
  最小间隙（阈值由用户给——取决于材料与工艺）、退化几何（半径 ≤0 的圆等）、
  文字未转曲线
- **解析覆盖 R10–R2018**：18 种实体，子类驱动的组码解释，未知 tag 原样保留；
  认不出的实体进 `Unknown` 不丢，语料解码率 98%
- **块与嵌套引用**：递归展开成世界坐标，图层 0 的实体继承引用的图层，
  循环引用截断报出
- **几何离散**：bulge 圆弧、椭圆、NURBS 样条折线化，容差是弦高、由调用方传
- **大文件流式**：分块喂入、内存不随文件增长，与整份扫描逐 tag 等价
- **三种形态**：库 + 命令行（退出码 0/1/2，含流式统计）+ 网页
  （在线版 <https://mik1e80.github.io/dxfkit/>，内置坏样例一键演示），
  跑的是同一份代码
- **语料回归**：47 个真实文件锚点钉进测试，改坏哪一层测试立刻指出来

## 与同类 MoonBit 项目的差异性

- **读 DXF 的 MoonBit 包：目前为 0。** `dxf` 关键词全生态只命中一个模块
  `f4ah6o/jww_parser`——它读的是日本 JW-CAD 的 `.jww` 专有格式，产出反而是
  **DXF 字符串**（源码里是 `jww_to_dxf` / `to_dxf_string`，只写不读）。
  dxfkit 是生态里第一个**读** DXF 的库，方向正好相反。
- **和 `cjcjwe/gcode-toolkit`（加工领域最近的邻居）：赛道互补、不重叠。**
  它处理 **G-code**——「图纸 → CAM → G-code」这条链的**下游**，源码里的
  分析对象是已生成的刀路（`MotionStatistics`：快移/圆弧计数、切割距离、
  进给率）。dxfkit 在**上游**：审图纸本身的几何成立不成立（轮廓闭没闭合、
  材料最窄多窄）——这些问题在 G-code 生成的那一刻就已经定型，下游的
  刀路审查看不见它们。输入格式、检查对象、能拦住的错误都不同。
- **和 `zgfzgf899/moonbit-vector-trace-plan`（名字最像的）：输入不同、
  语义不同。** 它从**位图**做矢量描摹 + 路径规划（源码的 `image.mbt`
  构造像素图，产出描摹出的路径清单）。dxfkit 从 **DXF 文件**出发，
  处理的是一整套 CAD 语义：图层（含冻结/继承）、块与嵌套引用、bulge
  圆弧与 NURBS 样条、文字未转曲线——描摹流程里不存在这些概念。
- 共同点只有「都在 MoonBit 里碰二维几何」；**对着图纸做加工前检查**
  这一层，生态里没有第二家。

## 移植或参考说明

原创项目。依赖只有 `moonbitlang/x`（读文件、退出码）和
`moonbitlang/async`（分块读，CLI 统计用），都在子包，库本体零依赖。
设计参考 DXF 框架 [ezdxf](https://ezdxf.mozman.at/)（MIT），**只参考
API 与能力范围、没有复制代码**；bulge 换算公式照其 `math/bulge.py`
移植，已在 [`THIRD_PARTY_NOTICES.md`](../THIRD_PARTY_NOTICES.md) 声明；
回归语料的 47 个 DXF 来自 ezdxf 仓库（MIT）。
