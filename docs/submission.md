dxfkit —— DXF 图纸加工前检查工具链

## 项目简介

dxfkit 是一个用 MoonBit 实现的 DXF（CAD 图纸）工具链，回答一个问题：
**这份图纸能不能上机床**（激光切割 / CNC 加工）。它把图纸解析成世界坐标
的折线几何，然后做加工前检查：轮廓闭合、自相交、重复切割、最小间隙、
退化几何、文字未转曲线。库本体零第三方依赖，同一份代码编译出库、
命令行、网页三种用法；47 个真实文件回归，206 项测试全过。

## 核心功能范围

- **加工前检查**：轮廓闭合（报缺口宽度和位置）、自相交、重复切割、
  最小间隙（阈值由用户给——取决于材料与工艺）、退化几何（半径 ≤0 的圆等）、
  文字未转曲线
- **解析覆盖 R10–R2018**：18 种实体，子类驱动的组码解释，未知 tag 原样保留；
  认不出的实体进 `Unknown` 不丢，语料解码率 98%
- **块与嵌套引用**：递归展开成世界坐标，图层 0 的实体继承引用的图层，
  循环引用截断报出
- **几何离散**：bulge 圆弧、椭圆、NURBS 样条折线化，容差是弦高、由调用方传
- **大文件流式**：分块喂入、内存不随文件增长，与整份扫描逐 tag 等价
- **三种形态**：库 + 命令行（退出码 0/1/2，含流式统计）+ 网页
  （在线版 <https://mik1e80.github.io/dxfkit/>，内置坏样例一键演示），
  跑的是同一份代码
- **语料回归**：47 个真实文件锚点钉进测试，改坏哪一层测试立刻指出来

## 预期场景

**一、上机床前的自检（核心场景）**。激光切割 / CNC 的小作坊和工作室接到
图纸，切第一刀之前先过一遍 dxfkit：轮廓没闭合、同一段线画了两遍、半径为 0
的圆、没转曲线的文字——这些问题在上机前暴露，省一次材料、省一次占机。
最典型的时刻：预览图看着好好的，切到一半轮廓散架。

**二、非技术岗位的「图纸体检」**。设计师、采购、业务不用装 CAD、不用懂
命令行——浏览器打开在线版，DXF 拖进去，左边预览右边报告。文件全程在
浏览器里算、不上传，敏感的客户图纸不出本机。

**三、进流水线的门禁**。批量图纸在进 CAM 之前先自动过一遍：CLI 退出码
0/1/2 直接挂脚本或 CI，有致命问题的图纸打回去，别浪费后面的工序。

**四、作为库，给 MoonBit 生态的其他人用**。MoonBit 里目前没有读 DXF 的
包——想做图纸统计、格式转换、加工预处理的人，可以直接依赖 dxfkit 的
解析层和世界坐标几何层。

**五、图纸档案室的快速盘点**。`dxfkit stats` 流式扫描、整份不进内存——
成百上千张老图纸扫一遍版本、段和规模，先盘清楚再决定哪些值得细查。

一句话定位：**dxfkit 不生成刀路（那是 CAM 的事）——它管的是「进 CAM
之前」和「上机床之前」那一步，把图纸本身的毛病先拦下来。**

## 差异性

**加工前检查**：能打开图纸的软件多，能回答「这份图纸能不能上机床」的少。
六项检查都对着生产里的真实事故：轮廓闭合（切完散架，报缺口宽度和位置）、
自相交（多切一道口子）、重复切割（同一刀切两遍，激光会烧焦）、最小间隙
（材料太窄扛不住）、退化几何（半径 ≤0 的圆、零长度线）、文字未转曲线
（机床不认字符串）。检查在**展开后的世界坐标折线上**做——块引用已摊平、
曲线已离散，预览和检查看的是同一份几何，不会「报告说有、图里找不到」。
只报告不修改，措辞不替用户打包票（没问题时说的是「这次检查没发现问题
（检查项有限，不构成保证）」）。

**最小间隙**（对应 stlkit 的壁厚）：三维里打射线量壁厚，二维里在平面内
量轮廓净距——同一个思路，3D 投到 2D。只在**会被切的图层**上查（冻结图层
本来就不切）；端点相接串成一条轮廓的邻居不误报；阈值由调用方给——1 毫米
的钢和 1 毫米的纸板不是一回事，没有通用默认值。

**认不出的东西不丢**：DXF 上百种实体，本项目解码 18 种，之外的进
`Unknown` **保留原记录**——报告能说「有多少实体没看懂」，而不是假装
图纸只有我看得懂的这些（语料解码率 98%）。多边形网格这类「按多段线
解析会出假几何」的类型，宁可当未认出去报告，也不生成错线。

**图层 0 继承（DXF 的老规矩）**：块内画在图层 0 上的实体继承引用的
图层。不实现这条，块画的轮廓会全落回图层 0，按图层过滤加工对象就全错了。
嵌套块引用按仿射矩阵复合展开，自引用 / 循环引用截断并报出。

**容差是参数，不是常量**：图纸单位跨度极大——语料里就有 `$INSUNITS=6`
（米）的图纸，而机加工图纸常常是毫米甚至微米。写死「1e-6 就算同一个点」，
米制图纸上会把分开的点焊在一起、微米图纸上会把一个点当成两个。凡是判
「相等 / 重合 / 闭合」的地方，容差一律由调用方传。

**解析器永不 panic**：产出「图纸 + 一串警告」——读了 90% 然后告诉你哪里
坏了，比抛异常什么都没读出来有用。编码判断有真实陷阱案例：新版文件里
失效的 `$DWGCODEPAGE` 会骗人（AC1027 的文件声明着 ANSI_1252，照它解会把
UTF-8 中文解成乱码还不报错）——判断顺序先看版本、再看代码页。

**流式扫描**：分块喂入、内存不随文件增长（固定 256KB 一块；
`moonbitlang/x/fs` 只能一次读完，走 async 的 `read_at`）。正确性有硬证据：
**流式与整份扫描在 47 个语料文件上逐 tag 等价**（块大小故意取奇数，把
`\r\n` 劈在中间测），600KB 合成文件手算的 tag 数逐字对上。

**曲线离散对着源码核**：bulge（凸度）→ 圆弧的公式照 ezdxf 的
`math/bulge.py` 移植，出处已进第三方声明；NURBS 求值用 de Boor
（NURBS Book A3.1），含有理权重。**方向约定用测试钉死**（b>0 = 逆时针、
半圆从弦下方过）——这个符号错了，所有带圆弧的轮廓都会镜像。离散容差是
**弦高**（弧中点到弦的距离），小圆自动多分段、大圆少分段。

**纯 MoonBit，没有 FFI**：native / wasm / js 三个后端都能跑；库本体
零第三方依赖（`moonbitlang/x`、`async` 只在 conformance 和 cli 子包）。

**网页版是同一份代码**：不是 JavaScript 重写的，是
`moon build --target js` 编译出来的——网页、命令行、库三者的结论逐字
一致；全程在浏览器里算，文件不上传；内置一张故意画坏的样例一键演示。

**结论可执行**：CLI 退出码 0/1/2（有致命 1、读不了 2），报告行是
`[致命] [检查项] 说明` 的固定格式，可以直接挂进流水线。

**206 个测试、`moon check --target all --deny-warn` 零警告**：47 个真实
DXF 文件（ezdxf 语料，MIT）的锚点钉进测试（339,913 个 tag、5,524 个
实体、检查 1 致命 / 122 警告）——任何一层改坏了，测试会立刻指出是哪个
文件、哪个数字对不上。

## 对比说明

**和 ezdxf（Python 生态最完整的 DXF 框架，MIT）**：设计上参考它最多——
参考的是能力范围与 API 设计，没有复制代码（bulge 公式的移植出处也在
第三方声明里）。三类客观差别：**定位**上它是数据保真库（读进来、改、
原样写回去，`audit` 查的是数据完整性），dxfkit 是加工视角的工具（只读
不写，检查项全部围着「能不能切」）；**能力**上加工前检查是它能力清单上
真实存在的空缺，而它有的二进制 DXF、写回文件、上百种实体，本项目没做的
就如实标「没有」；**生态**上 MoonBit 里读 DXF 的包目前为 0，加工方向
只有 `cjcjwe/gcode-toolkit`——它审的是加工链**下游**的 G-code 刀路，
和审图纸的上游互补。

逐项对比表（版本覆盖、写回、几何求值、渲染、流式、形态等）在仓库
[`COMPARISON.md`](../COMPARISON.md)；和同类 MoonBit 项目（jww_parser、
gcode-toolkit、vector-trace-plan、step 等）的源码级核对在同一份文档的
「MoonBit 生态」一节。
